Objet : Stage — Point d'avancement : le prototype Copilote IA Juridique est fonctionnel (étape par étape + exemple d'analyse)

Bonjour,

Je vous fais un point détaillé de l'avancement du stage, étape par étape, avec un exemple concret d'analyse réalisée pour illustrer le travail. Tout ce qui est décrit ci-dessous est fonctionnel et vérifié par des tests automatisés.

1. Ce que j'ai construit, étape par étape

Étape 1 — Lecture des documents
- Gestion de plusieurs formats : PDF (natif), Word (.docx), images (JPG/PNG), texte (.txt).
- Détection automatique du type de document : pacte d'associés, statuts, procès-verbal, modification statutaire, ou autre.
- Évaluation de la qualité de lecture : document illisible, scan de mauvaise qualité (OCR peu fiable), page manquante, document incomplet.

Étape 2 — Extraction des informations
- Extraction automatique des dates, montants, organisations/parties, références d'articles et des clauses.
- Découpage des textes en clauses titrées (agrément, cession de parts, non-concurrence, veto, etc.).

Étape 3 — Base juridique et références officielles
- Création d'une base juridique structurée (18 entrées : 10 sur le droit des sociétés, 8 sur les pactes d'associés), avec schéma, articles réels, mots-clés et règles associées.
- Chaque référence juridique pointe vers la source officielle (Légifrance) avec lien. Toutes les références fictives de départ ont été supprimées : le système ne signale plus aucune référence inventée (0 référence fictive dans les rapports).
- Le service PISTE de Légifrance est prévu dans l'architecture (mode lien actif, appel API à brancher avec un jeton).

Étape 4 — Règles de contrôle et comparaison entre documents
- 8 règles de contrôle déterministes : clause d'agrément, clause de sortie, droit de veto, majorités de décision, non-concurrence, contradiction pacte/statuts, clause de blocage, pouvoirs du gérant.
- Chaque anomalie comporte : explication simple, nature du contrôle, priorité (bloquant / important / alerte), conséquence possible, source juridique, correction recommandée, documents à vérifier, validation humaine requise.
- Comparaison croisée entre deux documents (pacte vs statuts) : dates, montants, parties, clauses, avec sévérité.
- Niveau de risque global : faible / modéré / élevé.
- Amélioration récente : le comparateur distingue désormais correctement les mêmes acteurs libellés différemment. Exemple : « SARL TOP LEGAL CONSEIL » dans le pacte et « STATUTS DE LA SOCIETE TOP LEGAL CONSEIL » dans les statuts ne génèrent plus de fausse alerte (c'était un faux positif auparavant, corrigé).

Étape 5 — Rapport de contrôle
- Rapport structuré et exploitable par un juriste : documents analysés, informations principales, anomalies présentées une par une, incohérences, niveau de risque, recommandations, points à valider.
- Export en PDF, Markdown, JSON et texte.

Étape 6 — Validation humaine
- Le juriste peut approuver, rejeter (avec motif) ou modifier chaque anomalie ; un taux de validation est calculé.
- La décision finale reste toujours à la charge du juriste ou du formaliste.

Étape 7 — API REST et interfaces
- API REST (FastAPI) prête pour l'intégration : POST /analyze (un ou plusieurs documents), GET /report/{id}, POST /validate/{id}/{anomalie}, GET /health. Documentation interactive sur /docs.
- Trois façons d'utiliser l'application : interface web (Streamlit), ligne de commande (CLI), API REST.
- Assistant conversationnel : on peut poser des questions sur le document analysé ; les réponses sont toujours basées sur le contenu du document.
- Enrichissement IA optionnel (Groq en priorité, repli local automatique) : sans clé API, l'application fonctionne à 100 % en local, aucune donnée n'est envoyée à l'extérieur, et l'IA ne cite jamais une référence inventée.

Étape 8 — OCR des images et PDF scannés
- Vérifié de bout en bout : une image ou un PDF scanné est lu par OCR (Tesseract + français), le texte est extrait et la qualité de lecture est évaluée (OCR faible si le résultat est peu fiable). Les deux tests OCR automatisés passent.

Qualité globale
- 73 tests automatisés, tous au vert.
- Architecture modulaire et évolutive : lecture, extraction, comparaison, règles, base juridique, IA, rapport, validation, API sont des couches séparées et remplaçables.

2. Exemple concret d'analyse réalisée

Pour vous montrer le résultat, voici un test réalisé sur deux documents d'un même dossier : les statuts d'une SARL et le pacte d'associés.

Documents analysés : statuts_sarl.pdf + pacte_associes_sarl.pdf
- Niveau de risque global : ÉLEVÉ
- Anomalies détectées : 3
  - Anomalie 1 (bloquant) : aucune clause d'agrément trouvée — source : Art. L228-23 — correction : ajouter une clause précisant la majorité requise pour l'entrée d'un nouvel associé.
  - Anomalie 2 (important) : aucune clause de sortie (drag-along / tag-along) identifiée — source : Art. 1103 C. civ — correction : envisager une clause de sortie conjointe pour protéger les associés minoritaires.
  - Anomalie 3 (important) : aucun mécanisme de résolution de blocage (médiation / arbitrage) — source : Art. 1530 C. proc. civ — correction : ajouter une clause de médiation préalable et une clause compromissoire.
- Incohérences entre documents : 0 (les acteurs du pacte et des statuts sont correctement reconnus comme identiques)
- Références fictives : 0 — toutes les références citées sont réelles et reliées à Légifrance.
- Validation humaine : les 3 anomalies sont présentées au juriste pour approbation, rejet ou modification.

Deuxième test : un manuel de droit (Introduction au droit)
- Le système a bien identifié qu'il s'agit d'un document de type « autre » (manuel/cours) et a extrait les informations (dates, organisations). Les entités sont affichées comme informatives. Point de vigilance identifié : les règles de société (clauses d'agrément, de sortie…) restent signalées même pour un cours ; je prévois de les neutraliser lorsque le document n'est pas un acte de société. C'est la prochaine amélioration.
